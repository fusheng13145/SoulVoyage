## 04 会话与令牌

| 检查项 | 现状 | 位置 | 结论 |
|---|---|---|---|
| 令牌生成 | JWT，`jjwt 0.12.6`，HMAC（`signWith(key)` 按密钥长度自动选 HS384/HS512，实测 HS512）；claims：`jti`/`sub`/`role`/`typ`/`iatms`/`iat`/`exp` | `JwtService:63-73` | ✅ 用了成熟库，无自研 |
| 密钥长度 | 启动即校验 `<32 字节则抛 IllegalStateException` | `JwtService:43-45` | ✅ 已验证 |
| 存放位置 | 后端不落 cookie；前端 `localStorage` 同时保存 access+refresh（`api/http.ts:28-29/61-62`） | `soul-frontend/src/api/http.ts` | ⚠️ XSS 可窃取；无 HttpOnly 保护（因为根本不用 Cookie）。另：刷新有"单飞"保护（`tokenAtStart` 比对，`http.ts:50-53`），并发刷新不会互相踩掉 —— 这点做得对 |
| 有效期 | access **30m**、refresh **7d**；`expiresIn` 随响应返回 | `application.yml:64-65` | ✅ |
| 退出登录 | 以当前时刻写 `jwt:epoch:{userId}`，**该用户此前所有会话立即失效**（不依赖客户端交回的令牌） | `JwtService:127-157` | ✅ **实测**：登出后旧 access 401、旧 refresh 401 |
| 修改密码 | 同上 `revokeAll` | `AccountService:87-89` | ✅ `AuthHardeningTest#deletionRequestAndPasswordChangeRevokeLiveSessions` |
| 账号注销 | `revokeAll` + 冷静期满销毁 DEK | `AccountService:54`、`M9CryptoZoneTest` | ✅ |
| refresh 轮换 | 用后即拉黑（`jti` + 剩余 TTL）；检测到已拉黑的 refresh 再用 → **全局吊销** | `JwtService:116-124`、`AuthService:98-112` | ✅ `AuthHardeningTest#refreshRotationAndReuseRevokesAllSessions` |
| 类型混用 | refresh 当 access 用 → 401（`typ` 校验） | `JwtService:97-99` | ✅ `AuthHardeningTest#wrongTypeTokenRejected` |
| Cookie 属性 | 不使用 Cookie，`allowCredentials(false)` | `SecurityConfig:85` | ✅ 不适用（非缺陷） |
| 框架/自研 | Spring Security 过滤器链 + jjwt；限流/吊销用 Redis（Lua 原子脚本） | — | ✅ |
| Redis 故障降级 | **读**失败 → 视为"未拉黑、epoch=0"，即吊销在 Redis 故障期间失效；**写**失败 → 503 | `RedisGuard`、`JwtService:78/136` | ⚠️ 可接受但需明确决策（见下） |
| 多设备会话管理 | 无会话列表；登出只能"全端下线" | — | ⚠️ 产品取舍，非漏洞 |

**建议（按风险排序）**
1. **令牌存内存 + 短期 access**：refresh 放 `HttpOnly; Secure; SameSite=Lax` Cookie（同域）可显著降低 XSS 拖库损失；当前 `localStorage` 方案在 XSS 下等于全量失守。
2. Redis 读降级改为 **epoch 检查 fail-closed**（Redis 不可达时拒绝写操作类接口，或至少拒绝高风险接口），把"吊销失效"的窗口关掉。现在的降级是"可用性优先"，写进了注释，但安全影响没有被显式记录。
3. 增加"当前设备会话"列表与单端下线（可选）。

**实测缺陷证据**

```http
POST /api/v1/auth/register {"username":"pw153537","password":"aaaaaaaa","nickname":"weak"}
→ 200 {"code":0,...,"userId":4}          # 8 位纯字母通过
```

**结论与修复**
- ⚠️ **弱口令**：口令策略只有长度。建议引入"最小强度"：长度 ≥8 且（含字母+数字 或 ≥12 位），并接入常见弱口令表（可用 `OWASP common passwords` 列表，10 万条内内存比对即可，不要自研算法）。
- ❌ **登录锁定可被绕过**：锁定键含 `ip`，而 `AuthController.clientIp:62-65` 取 `X-Forwarded-For` 的**第一段**；nginx 用 `$proxy_add_x_forwarded_for`（客户端值在前、真实 IP 在后），因此攻击者自带 `X-Forwarded-For: 1.2.3.4` 即可每次换"IP"。实测换 XFF 后同一账号第 6 次用正确口令直接 200。**修复**：改成"仅信任最右一段"或用 `X-Real-IP`（nginx 已设 `X-Real-IP: $remote_addr`），并叠加"单账号全局失败计数"（不绑 IP）。
- ⚠️ **管理员账号无引导流程**：需要明确"生产管理员如何创建、初始口令如何设置、是否强制二次校验"。当前 `deploy/tools/*.mjs` 写死 `admin` / `Passw0rd!2026`（见 15），说明开发库管理员大概率就是该口令。
- ⚠️ **框架噪声**：启动日志出现 `Using generated security password: …`（Spring 默认 `InMemoryUserDetailsManager`）。因为没开 `httpBasic`/`formLogin`，这条认证路径实际不可用；但会在日志里制造"疑似后门口令"的误导，建议 `@SpringBootApplication(exclude = UserDetailsServiceAutoConfiguration.class)` 或显式提供 `UserDetailsService`。

## 07 注入风险

| 类型 | 检查结果 | 位置/机制 | 证据 |

| SQL 注入 | **无风险**。全部走 JPA 派生查询与 `@Query` JPQL（`like concat('%', :kw, '%')` 之类均为命名参数绑定），无 `createNativeQuery`、无 `JdbcTemplate`、无字符串拼 SQL | 37 个 Repository 接口 | 全量 grep `@Query`/`Statement` 仅命中参数化 JPQL；实测 `q=' OR 1=1--` 返回空集、无异常、无 SQL 报错 |

| 命令注入 | **无**：全仓库无 `ProcessBuilder` / `Runtime.exec` / `sh -c` | — | 全量 grep 0 命中 |
| HTML / 模板注入 | 无服务端模板引擎渲染用户输入；前端无 `v-html` / `innerHTML`（仅测试文件出现） | Vue 默认插值转义 | 前端全量 grep |
| Prompt 注入 | 用户正文永远作为 **user 消息**，系统提示来自静态模板，二者不拼接 | `OpenAiCompatibleClient:138-139`（`role=system` / `role=user` 分列） | 代码；`OutputValidator` 对输出做 JSON 结构校验与重试 |
| 日志注入 | 日志用 SLF4J 占位符，无字符串拼接；但用户输入含换行时会污染单行日志 | `AuthService` 等 | ⚠️ 低风险；如需彻底可对 `\r\n` 做替换（非必须） |

**残留问题（非注入，但值得修）**
- 原先此处写的是"日记 `q` 的 `%`/`_` 未转义"——**第二轮核实后纠正**：日记搜索 `DiaryService.list` 是**解密后用 `content.contains(q)` 做内存过滤**，根本没有 SQL LIKE，不存在通配符放大。全仓库唯一的 `like concat('%', :kw, '%')` 在 `UserRepository:34-35`，服务于**管理端用户搜索**（username/nickname），JPQL 无 `ESCAPE`：`%` 会把条件放宽成"匹配全部"，`_` 会变成单字符通配。影响仅限"管理员自己输入了通配符"，既非注入也不会越权（结果仍是本就有权看的用户列表），**属低危提示，不修也不阻断上线**；若要彻底可在绑参前对 `%`/`_` 做转义并加 `escape '\'`。见 §21.3。

## 12 业务逻辑与并发

**本项目没有下单、支付、退款、领券、提现、库存、金额**，所以"超卖/重复扣款/金额篡改"这类风险**不适用**。以下是真实存在的核心流程：

| 流程 | 后端是否重算/重校验 | 防重复提交 | 并发保护 | 关键步骤可否跳过 | 结论 |
|---|---|---|---|---|---|
| 任务提交（日记/复盘/演练） | 管线与 payload 由枚举/规则校验，不接受客户端传"阶段/结果" | `clientReqId` + 唯一索引 | ✅ **第二轮已修**：`TaskGateService` 单事务 + 用户行锁；60 路并发实测 4→2（见 §21） | 不能：步骤由 Pipeline 顺序驱动，客户端只能"重试/取消" | ✅ |
| 日记落库 | 长度、日期归属（`BusinessCalendar` 业务时区）由服务端算 | 每日一篇（按 `record_date` 判重） | DB 约束 | 不能跳过隐私同意（`policyVersion`） | ✅ |
| 情绪打卡 | 枚举/范围校验；`rating` 影响画像点由服务端写 | 唯一键 `(user_id, check_date)`；重复提交=**覆盖**，不重复计分 | ✅ **第二轮已修**：同用户行锁把 find-or-create 串行化；10 路并发实测 7 个 500 → 全部成功 | 不能补未来日期（`makeup` 有日期上限） | ✅ |
| 计划项完成 | 是否"今日项"、是否已完成由服务端判 | 幂等（已 done 不重复加分） | 乐观锁 `version` | 不能跳过前置（须有 active 计划） | ✅ |
| 导出（一次性链接） | 明文只在内存，快照存 Redis 密文 | 5 分钟 TTL + 领取即焚 | Redis Lua 原子 `GET+DEL` + 属主判定；`InMemoryExportStore` **第二轮已改为 `compute` 原子取走** | 不能拿别人的 `fileId` | ✅ |
| 危机干预 | 等级/生命周期由服务端状态机推进 | — | 状态机 + 冷却 7d | 用户不能"关闭"危机态 | ✅ |
| 内容发布 | 版本号、生效时间服务端算 | 版本 bump | ✅ **第一轮误判，第二轮纠正**：发布带 `baseRevisionId` 基线校验，不匹配返回 409/2003（实测），不是"最后写赢" | 不能绕过草稿→发布 | ✅ |
| 注销执行 | 冷静期由服务端算 | 定时任务 + 分布式锁 | Redis 锁（降级单机） | 用户不能立即销毁 | ✅ |

**举例说明风险**
1. 用户脚本并发打 `POST /tasks` 10 次：`countActive` 都读到 0/1，可能同时通过检查，实际落 5–6 个活跃任务 → LLM 成本翻倍、队列拥塞。**实测确认**（60 路并发 4 个 202，tasks 2→6），**已在第二轮修复**：`countActive` 与 `save` 收进 `TaskGateService` 单事务并对用户行加 `FOR UPDATE` 锁。
2. `InMemoryExportStore.take` 两线程同时命中同一 `fileId` 都可能返回数据 → 破坏"一次性"。**代码确认存在**（get 后再 remove），**已在第二轮改为 `ConcurrentHashMap.compute` 内一次完成校验+取走**，并新增 8 线程 ×40 轮并发用例。

### 22.2 协议变更（前后端契约，必须一起发布）

- **浏览器端**：`POST /auth/login|register|refresh` 的响应体里 `refreshToken` 恒为 `null`；refresh 只经 `Set-Cookie: sv_rt=...; Path=/api/v1/auth; HttpOnly; SameSite=Lax; Max-Age=604800`。`POST /auth/refresh` 支持 body 优先、Cookie 兜底；**走 Cookie 时校验 `Origin` 白名单**（无 Origin 放行），外来 Origin 直接 403。`POST /auth/logout` 无论服务端吊销成败都先下发 `Max-Age=0` 清 Cookie。
- **为什么加 `Origin` 校验**：`SameSite=Lax` 已挡跨站 POST，但旧浏览器/特殊场景可能失效；这道校验是第二层保险，也让"无 Origin 的原生客户端"与"有 Origin 的浏览器"能被明确区分。
- **原生小程序端**：判定条件是 **`X-Client-Type: miniprogram` 且无 `Origin` 头**，仍拿 body 令牌（小程序无浏览器页面、无 XSS 面）。浏览器伪造这个头也拿不到 body 令牌——同源 POST 必带 Origin（实测见 §22.3）。
- **Web 端改造**：`api/http.ts` 删除 `TOKEN_KEY/REFRESH_KEY`，access 只放模块内存（`get/set/clearAccessToken` + `ensureSession()`），refresh 请求不再带 body、改 `withCredentials`；页面刷新后由 `ensureSession()` 静默续期一次再接路由守卫（`router.beforeEach` 改为 async，`App.vue` 用 store 的 `authed`）。三个 spec 同步重写。
- **小程序端改造**：H5 构建（`process.env.UNI_PLATFORM === 'h5'`）走 Cookie；原生构建自动带 `X-Client-Type: miniprogram` 走 body。`setTokens` 不再写入 `null` refresh；`refreshOnce` 在 H5 下允许空 body（后端回落 Cookie）；`bootstrap` 先 `ensureSession()`。
- **契约与类型**：`soul-backend/openapi/openapi.json` 只有两处变化（refresh 请求体由 required 变可选、logout 的 `Authorization` 头变可选），已 `-Dopenapi.update=true` 重生成，两端 `gen:api` 同步，`vue-tsc` 通过。
